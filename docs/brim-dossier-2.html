1Core architecture

The constraint that decides the topology

Fact Privacy permissions on macOS attach to code identity, not to a user. A command-line tool is a separate binary with a separate identity, so it needs its own grant; Apple's guidance on shipping entitled command-line tools is that they have nowhere to carry a provisioning profile and must be packaged inside a bundle-like structure to pick one up.17 Inference If Brim's CLI, its MCP server and its app are each independent processes touching the filesystem directly, the user is asked for Full Disk Access three times, and the three can disagree about what they saw. That single fact eliminates the most obvious architecture.

A. One app, thin helperB. Shared library, several peersC. One service, many clients
ShapeEverything in the app; helper for root workCore compiled into app, CLI and MCP server; they share the database fileApp, CLI, MCP server and intents are all clients of one local service that owns the index and the engine
Permission grantsOne, but the CLI has to be the appOne per binary. Three prompts, three identitiesOne
Index consistencySingle ownerMultiple writers on one SQLite file; readers fine under WAL, writers contendSingle writer, single truth
Where safety livesIn the appIn three places, and they can driftOne place, in front of every caller
CostLowestLowOne more process and an IPC boundary to get right
Agent storyPoor — agents can't drive a GUIWorkable but unsafe: each peer can act aloneNatural — an agent is just another client

Challenge to C

Three processes for a utility written by one person is how projects die. Cross-process debugging is miserable, XPC interfaces are tedious to evolve, and every release now has to keep three binaries version-compatible.

The security objection is sharper. A local service is a permanently reachable endpoint holding Full Disk Access. If its caller check is weak, any process on the machine inherits that reach. This is not theoretical for Mac utilities: the privileged helper in a widely used open-source Mac system monitor accepted every incoming connection without validating the caller, exposing fan control and a powermetrics wrapper with a command-injection flaw that gave arbitrary code execution as root.11

And there is an optics problem volume I should have anticipated: a tool whose pitch is "see what runs on your Mac without being asked" that installs something which runs on your Mac without being asked.

Re-evaluation

The maintainability objection is answered by making the service thin and the core a library. The engine is one Swift package with no UI and no privilege; the service is a few hundred lines that owns a database handle and exports an interface. Debugging the engine does not require the service at all, because the engine is testable in isolation against a fixture tree (§3).

The reachability objection is answered by identity, not by obscurity. Fact macOS 13 added -[NSXPCConnection setCodeSigningRequirement:], which Apple's developer support explicitly recommends as the fix for this exact class of problem; the C API equivalent arrived in macOS 12, and there are further changes for Swift's XPCListener in macOS 26.9 Process identifiers must not be used, because they are recycled and the check can be raced.10 With a code-signing requirement applied in both directions, the endpoint is reachable only by Brim's own signed components.

The optics objection turns into a feature. Brim's service does not need to outlive the app for the app's own work — an XPC service inside the bundle is launched on demand and dies with its client. Only two features genuinely need persistence: energy sampling and scheduled reporting. Both are opt-in, both register visibly, and Brim lists itself in its own background-items view alongside everything else. A tool that polices background items and exempts itself is not trustworthy; one that shows itself in the list is making an argument.

Decision — the component model

One engine, one service, many clients, one gate.

  • Brim Core — a pure Swift package: no UI, no privilege, no network, no global state. Identity, footprint, graph, evidence, safety, planning, verification. Everything else is a shell around it.
  • Identity Layer — resolves "what is this?" to a stable key: bundle identifier, Team ID, code-directory hash, receipt identifier, launchd label, coalition. Every artefact and every actor in the system is named by this layer, and nothing downstream matches on strings.
  • Artifact Graph — nodes are artefacts (paths, launchd jobs, background-item records, privacy grants, running processes, receipts); edges are evidence relations carrying a tier. Volume I's tiers are edge labels here, which is why the same structure serves uninstall, reset, leftovers and background items without special cases.
  • Application Footprint — a projection over the graph for one identity. Not a stored object; a query. This matters: a footprint computed on demand can never go stale.
  • Persistent index — one SQLite database, one writer, inside the service.
  • Evidence engine — a pure function from graph to tiers. Deterministic, snapshot-testable, version-stamped per macOS release.
  • Safety engine — the only component permitted to emit a plan. Applies the tier defaults, the shared-file veto, the capability checks, and the cost-of-error annotation.
  • Plan — a first-class, persisted, content-addressed, locally signed object: ordered steps, each with target identity, evidence, tier, expected byte delta, reversibility, and required privilege. A plan is readable, storable, diffable and replayable.
  • Transaction and rollback — plan, then journal, then apply, then verify. The journal is written before the first mutation, so a crash mid-apply is recoverable on next launch rather than mysterious.
  • Verification — re-observe, measure the filesystem delta, reconcile against the plan's expectation, record the difference honestly.
  • Background observation — differential snapshots plus filesystem events while the service is alive. No content inspection, no install hooking.
  • Privileged helper — smallest possible vocabulary (§6). It does not accept paths.
  • Adapters — SwiftUI app, CLI, MCP server, App Intents. None of them contains logic. All of them speak plan.

Inference The plan object is doing most of the work in this design. It is the audit record, the agent interface, the undo source, the support artefact and the test fixture, and it is the reason the capability boundary in §2 can be enforced rather than merely intended.

2Agent-native Brim

The question is not how an agent talks to Brim. It is what an agent is structurally incapable of doing.

What the threat actually is

Fact Indirect prompt injection — instructions hidden in content the agent reads rather than typed by the user — is the dominant attack class against tool-using agents. A 2026 meta-analysis across adaptive attacks found success rates against state-of-the-art defences above 85%, with most defences achieving under 50% mitigation.29 Real incidents in 2026 include a proof-of-concept against coding agents where a repository with no malicious code convinces the agent to run a setup step that fetches and executes a payload,31 and a disclosed chain against Anthropic's own GitHub action composing authorisation bypass, indirect injection and environment exfiltration.30

Inference Brim has a version of this that is worse than most, and it is specific enough to name. Filenames are attacker-controlled text. Any application, including a malicious one, can create a directory whose name is a paragraph of instructions. Brim's entire job is to read those names and hand them to something that reasons. A cleaner with an agent interface is an injection surface by construction, and no amount of filtering fixes it — the security literature is consistent that filtering has a ceiling.29

Fact The mitigation the research converges on is architectural rather than linguistic: separate the reasoning layer from the layer that holds the credentials. A model that analyses and produces a structured recommendation, but cannot itself execute the resulting action, cannot be weaponised into performing it.30

Challenge to the obvious answer

The obvious answer is "ship all three and let each host's consent flow protect the user". That is wrong twice over.

First, it outsources the safety property to software Brim does not write. MCP's own specification is explicit that the protocol cannot enforce its security principles and that hosts should build consent flows.2 A "should" in someone else's client is not a boundary. National security guidance published in 2026 on MCP deployments catalogues exactly this gap, including unverified task propagation between components and weaknesses in session handling.3

Second, a CLI with useful verbs is a destructive primitive with a friendly name. If brim remove exists, an agent that has been injected will run it, and a human who approves a plausible-looking command will let it. The consent that matters is consent to this specific set of files, and a command line cannot express that.

There is a third, quieter problem. Volume I's Tier C items are the ones requiring human judgement. An agent is exactly the wrong thing to adjudicate them and exactly the thing most likely to be asked to.

Re-evaluation

The surfaces are fine; the vocabulary is the problem. If the only verbs are inspect, plan, request approval, apply an approved plan and verify, then every property above changes. An injected agent can produce a plan — which is inert. It can ask for approval — which raises Brim's own window showing the real file list. It cannot approve, because there is no call that approves.

This also resolves the Tier C worry without a special rule: an agent cannot select a Tier C item because selection is the safety engine's job, and the safety engine does not consult the caller.

On unattended automation: it is safe for anything read-only and unsafe for anything else, so the intents split along that line rather than being excluded wholesale.

Supporting rules, all enforced in the service rather than in the adapters:

  • Everything read from disk is data. Paths, display names, property-list values and process names are delimited and labelled as untrusted when they reach any model or any tool result. Brim treats its own index as hostile input.
  • Model output cannot name a target. A model may reference steps of an existing plan by identifier; it can never emit a path that the safety engine did not already produce. This removes the injection payoff entirely: the worst an injected model achieves is a misleading sentence about a plan the user can read.
  • No network listener. The MCP server is a local process speaking over standard input and output, launched by the host; with that transport the server inherits the host's permissions rather than exposing a socket.5 Cloud agents reach Brim only through a local host the user is running. Brim ships no HTTP transport — the 2026 revision's move to stateless HTTP is excellent for hosted services and wrong for a root-adjacent local utility.1
  • Agent actions are labelled in History, with the requesting identity recorded, so "what did the agent do" is answerable.

Staging. The plan object, the approval token and the service-side capability check must exist from the first line of code; they are not retrofittable. V1 ships the CLI and the MCP server with inspect, plan, explain, request-approval, apply and verify, plus read-only App Intents and one intent that opens a plan for review. Standing policies that pre-authorise a narrow class of future plans, unattended reporting automations, and anything resembling autonomous maintenance wait until the approval path has been in the field long enough to trust.

3Technology stack

Interface layer

Fact The numbers here are unambiguous. A 2026 comparison rendering 100,000 rows on macOS measured NSTableView at 45 MB and a constant 60 frames per second, SwiftUI's List at 800 MB and 22 frames per second, and a LazyVStack in a scroll view at over 1.2 GB and under 20 frames per second. The stated cause is that List on macOS is backed by NSCollectionView, which creates views lazily but does not reclaim them aggressively, so memory tracks total rows rather than visible ones.18 Fact On Apple's own forums, developers report SwiftUI Table performance regressing on macOS 15.5 and 26 despite session claims of improvement, with the advice being to use NSTableView directly.19 Fact SwiftUI's body is main-actor and re-read on every state change, so any non-trivial work placed inside it blocks rendering.20

Recommendation SwiftUI for the shell, navigation, inspector, sheets and every view with a bounded number of subviews. NSTableView behind NSViewRepresentable for any list that can exceed roughly a thousand rows — leftovers, the file browser, the background-items list, the duplicate view. The boundary is a measured rule, not a preference, and it should be written into the project's conventions so it is not relitigated per view.

Language

The honest question is whether any part of Brim justifies Rust.

Challenge

The case for Rust is not really performance; it is correctness in the component that runs as root. Recursive deletion with symlink safety is precisely the kind of code where a memory-safe language with a strong ecosystem of audited primitives looks attractive.

Re-evaluation

That case does not survive contact with the specific bug class. The canonical recursive-delete vulnerability is not a memory-safety bug — it is a logic bug about symlinks, and it happened in Rust's own standard library, where remove_dir_all checked whether a target was a symlink and then deleted it, leaving a window an attacker could win within seconds.14 Language choice does not prevent it; using the right syscalls does (§6). Meanwhile the cost is real: a second toolchain inside a notarised privileged helper, for one developer.

Decision

Swift throughout, with C shims where the importer is inconvenient. Rust fluency is not a reason to introduce Rust here; the platform surface Brim touches is C and Objective-C, and the one place Rust's guarantees would matter turns out to be a logic problem rather than a memory problem.

4GPU, Metal, and what actually makes Brim fast

Where the time really goes

Fact A direct measurement on an M4 Pro with a 1 TB internal drive, hashing two 20 GB files read from disk, gave 10.7 seconds for SHA-256 and 8.2 seconds for BLAKE3 — about 25% faster from disk, against the several-fold advantage BLAKE3 shows in memory-bound benchmarks.24 Fact The gap narrows on Apple silicon specifically because ARM cryptography extensions accelerate SHA-256, while BLAKE3 has no dedicated silicon and relies on general vector width and core count.25

Inference Duplicate detection is a storage-bandwidth problem wearing a cryptography costume. If changing the hash function — the single biggest lever available — buys 25% on real files, then moving hashing to the GPU, which requires pushing the same bytes across the same memory system, cannot buy meaningfully more. The entire GPU discussion for hashing is settled by one measurement.

WorkloadCPU-firstHybridGPU-heavyVerdict
Window chrome, animation, scrollingAlready GPU-composited by Core Animation——Nothing to do. Custom Metal here would replace working system code with code Brim must maintain across two Liquid Glass revisions

Challenge to CPU-first

It sounds like an excuse for not building anything impressive, and it assumes today's workloads. A storage view that renders a genuinely huge hierarchy fluidly, with continuous zoom, is the kind of thing that makes a utility feel expensive — and that is a rendering problem where a custom pipeline genuinely helps.

Re-evaluation

Partly fair, and the answer is to be precise about the threshold rather than to refuse on principle. Continuous zoom over a pre-aggregated hierarchy is hundreds of nodes on screen at any moment; the system handles that. A custom pipeline only pays when the node count on screen exceeds what the compositor can batch, which for a storage map means rendering detail below one pixel. That is a correctness problem, not a performance one.

The challenge does land on one thing: perceived speed is a real product attribute and it is not delivered by raw throughput. It is delivered by never blocking, by showing partial results immediately, and by never making the machine feel worse while Brim runs.

Decision — CPU-first, and spend the effort on what users feel

  • Read less. Bulk enumeration in one pass. Size classes first, then a sparse fingerprint of the head, tail and length, then a full hash only for survivors. Detect clone-shared extents before claiming any saving — a duplicate finder that counts cloned files as recoverable space is reporting fiction.
  • Never scan twice. One full pass, then event-driven deltas. The second launch should be near-instant.
  • Stream, never materialise. Memory bounded by working set, not by volume size.
  • Do not evict the user's cache. Large one-shot hashing passes read with caching disabled, so a duplicate scan across a few hundred gigabytes does not push everything the user was working with out of memory. Inference This is the most commonly skipped courtesy in this category, and it is the direct cause of the "my Mac got slow after running a cleaner" impression.
  • Yield to the system. Background quality-of-service for scanning so the scheduler can place it on efficiency cores; back off on thermal pressure and in low-power mode; declare long work as an activity rather than fighting App Nap.
  • Partial results immediately. The review queue populates as evidence arrives; no modal progress bar owns the window.

Budgets, stated as two-sided. Every performance target names both what Brim delivers and what it costs: first index under a minute on a typical machine at background priority; incremental refresh under two seconds; steady-state memory bounded regardless of volume size; measurable energy cost of a full scan published in Brim's own energy view. Recommendation Brim should be able to show its own line in its own energy list. A tool that reports what software costs and hides its own cost has not earned the feature.

5UI and information architecture

Fresh research, because the ground moved: Apple revised the design language three months ago.

What changed since volume I

Fact At WWDC 2026 Apple revamped Liquid Glass for iOS 27, iPadOS 27 and macOS 27 in response to criticism: reduced default transparency, a changed glass effect, changed sidebar corners on macOS, revamped app icons, and a user-facing slider that moves the interface between clearer and more heavily tinted glass.26 Fact The consistent guidance for the material is that it belongs on sidebars, toolbars, navigation chrome, floating panels and popovers, and does not belong on primary content areas, dense data displays such as tables and long lists, or text-heavy interfaces where readability matters.27 Fact Apple's own adoption guidance is that standard components pick up the new look automatically when built against the current SDK, that split views with sidebar, content and detail receive glass on the sidebar and inspector without custom work, and that content needs safe-area treatment to sit correctly beneath floating chrome.28

Console interfaces are tools of last resort. People open Activity Monitor when the fan is loud, and they close it when the fan stops. 6Security

Assets, and the one that is usually missed

Three obvious assets: root through the helper, broad read access through Full Disk Access, and the ability to delete. The missed one is the index itself. Inference A database listing every installed application, every support path, every background registration, every privacy grant and a history of energy behaviour is an excellent reconnaissance artefact — arguably more useful to an attacker than root on a machine they have already compromised. Brim must treat its own database as sensitive: owner-only permissions, no export without an explicit user action, and no inclusion in diagnostics by default.

The four vulnerability classes Brim will actually face

These are not hypotheticals. Each has a recent, documented instance in software of exactly Brim's shape.

ClassDocumented instanceWhat it means for Brim
Unvalidated helper callersA popular open-source Mac system monitor's privileged helper accepted every connection, exposing fan control and a powermetrics wrapper carrying a command-injection flaw that yielded arbitrary root execution11Validate with a code-signing requirement, never a process identifier.910 And never build a helper method that passes a caller-supplied string to a command line — this is the specific reason volume I's rejection of parsing powermetrics as root was correct for security as well as accuracy
Caller impersonation plus path swapA commercial macOS client's privileged helper combined improper certificate validation with a symlink swap during installation, giving local privilege escalation to root12Both halves must be closed. Both canonical instances of this bug are in Brim's exact feature set

Prevention

  • A helper vocabulary too small to abuse. The helper exposes one operation: execute step n of approved plan h. It does not accept paths, patterns, globs, or command strings. It reads the plan from a location only Brim's signed components can write, verifies the plan's signature and hash, and — this is the part that matters — re-runs the evidence and safety checks itself using the same core library, rather than trusting the caller's conclusions. A completely compromised application process still cannot persuade the helper to touch something the evidence does not support.
  • Identity on both ends. Code-signing requirements on both directions of every connection, applied before any interface is exported.9
  • Race-immune file operations. Open the parent directory without following links, operate relative to that verified descriptor, confirm the descriptor's device and inode match what the plan recorded, and refuse if anything moved. Never a check followed by an operation on a path string. This closes the class in 14 and 15 structurally.
  • Trash, not unlink, wherever the filesystem permits it, including for privileged items.
  • Bundles are data. Display names, property-list values, appcast URLs and icons read from scanned applications are never executed, never used to construct a command, and never trusted as instructions. Vendor uninstallers are revealed to the user, never run by Brim.
  • Update channel. Signature verification on every update, feed URL compiled in rather than read from anywhere, public key pinned, notarised and stapled builds, and a published code-directory hash per release so a user can verify the binary they hold. Given that volume I documented a fake distribution site pushing malware under a competitor's name, single-origin distribution is a security control, not marketing.
  • Dependencies. Two significant ones — a database layer and an update framework. Pin them, review their diffs, and keep signing keys in hardware. A utility with root access has no business carrying a large dependency tree.
  • Agent boundary. The capability table in §2, enforced in the service rather than in any adapter, plus the rule that model output can reference plan steps but never name a target.

Runtime detection

  • Append-only journal. Every executed step recorded with the plan hash, the requesting identity, the outcome, and the measured delta. This is the ledger volume I specified, extended to record intent as well as effect.
  • Self-verification on launch. Brim checks its own signature and the helper's; a helper whose version or hash does not match the app refuses to serve and offers reinstallation.
  • Shape anomalies. A plan whose breadth is unusual for its evidence profile, a run of rejected connections failing the signing requirement, repeated approval requests for the same plan, or a plan referencing paths outside every known domain — all logged and surfaced rather than silently handled.
  • Agent actions visibly distinct in History, so an unexpected pattern is legible to the user rather than buried.

Recovery

  • Crash-safe application. The journal is written before the first mutation; on next launch Brim reconciles it and offers to complete or roll back, rather than leaving a half-removed application.
  • Undo bound to reality. Before offering to restore, confirm the Trash items still exist; say "no longer recoverable" rather than failing.
  • Total self-removal. Brim can remove itself, its helper, its agent, its index and its registrations completely, and verify the result. Inference For a product whose claim is complete uninstallation, being unable to uninstall itself perfectly would be disqualifying; being able to demonstrate it is the cheapest credibility Brim can buy.

Decision — the minimum that makes Brim trustworthy

Five controls, and everything else is depth on top of them:

  1. A helper whose vocabulary cannot express an arbitrary deletion, and which re-validates independently.
  2. Code-signing requirements on both ends of every connection.
  3. Race-immune file operations using directory descriptors, never path strings.
  4. Trash-first, with an append-only journal written before the first change.
  5. Approval as a human-only capability with no programmatic path.

Inference Four of the five are the same control seen from different angles: never act on a name someone handed you. That is also, exactly, the safety model volume I derived for deciding which files belong to an application. The security architecture and the product thesis turn out to be one idea.

Challenge

"Change, not state" sounds disciplined and is quietly expensive: it requires history, which requires the index to persist and be trusted over months, which means every schema migration risks the feature. It also fails for exactly the user volume I identified as the target — someone installing Brim on an already-cluttered, migrated machine, who has no history at all.

Re-evaluation

The cold-start problem is real and already has an answer from volume I: the first run leans on present-tense evidence, and the historical layer compounds. Saying so plainly in the empty state is more honest than fabricating a trend. The migration risk argues for treating history as append-only observations with a stable shape, rather than as derived aggregates that must be recomputed — observations survive schema changes, summaries do not.

Decision

Everything local, no exceptions, no telemetry, no accounts. Default-visible: only findings that are both new and actionable. On demand: every trend. Non-existent: any score, any gamification, any comparison.

Recommendation Build one insight nobody else will ship: "you don't have a problem." When reclaimable space has not moved in months, when no new background items have appeared, when no application is an energy outlier — say so, and say it as a result rather than an absence. It is true more often than the category admits, it costs nothing to compute, and it is the single clearest signal that Brim's numbers can be trusted when they are not zero.

8Simplicity and the habit problem

Three models for how a utility earns a second launch.

Challenge to C

Software that never asks for attention gets forgotten, and forgotten software does not get recommended, updated or repurchased. C optimises for dignity and may optimise away the business. Every successful consumer utility has some recall mechanism.

Re-evaluation

The objection assumes engagement is the goal. Under the one-time-purchase model volume I recommended, it is not — there is no renewal to protect, which removes the structural incentive to manufacture attention. That is worth stating as a deliberate advantage rather than treating as a gap.

But the discoverability half of the objection stands, and it has a concrete answer that is not notification. Brim should already be present at each of the four moments a person needs it: when they drag an application to the Trash, when they install something, when they are low on space, and when the battery drains strangely. Presence at those moments comes from placement — a Finder extension, a Dock drop target, Spotlight actions through App Intents,6 a command-line entry point — not from reminders.

Decision

  • Immediate value with zero setup. The first window shows real, specific findings without any permission grant. No onboarding, no account, no tour.
  • One notification class, opt-in: something registered itself to run in the background that you did not install. Event-driven, rare, actionable. Nothing else, ever — no storage warnings, no weekly summaries, no "it's been a while".
  • No fear language anywhere. No red, no "your Mac is at risk", no percentage of health. Findings are described by what they are and what they cost.
  • Complexity lives in the inspector. Three depths (§5), every advanced capability reachable, none of it in the way.
  • Be where the moment is: Finder extension, Dock drop target, Spotlight actions, CLI.
  • Willing to say nothing needs doing (§7), which is the behaviour that makes the other results believable.
  • Measure the right thing. The success metric is whether Brim was opened at the moment it mattered and gave a correct answer, not how many days a month it was opened.

1 · Final Brim architecture

One engine, one service, many clients, one gate.

  • Brim Core — pure Swift package: identity layer, artifact graph, evidence engine, safety engine, planner, verifier. No UI, no privilege, no network, no global state. Linked by every other component, including the helper.
  • Brim Service — owns the index (one SQLite database, one writer) and is the only component that answers requests. Runs on demand as an XPC service inside the bundle for app-driven work. Persists only when the user opts into energy sampling or scheduled reporting, and then registers visibly and appears in Brim's own background-items list.
  • Brim Helper — privileged, installed only when a system-domain action first requires it, fully removable. Vocabulary: execute step n of approved plan h. Re-validates independently using Core. Never accepts a path.
  • Adapters — SwiftUI app, CLI, MCP server, App Intents. No logic; all speak plan.
  • The plan is the unit of work: signed, content-addressed, persisted, readable, diffable, replayable. It is simultaneously the audit record, the agent interface, the undo source, the support artefact and the test fixture.
  • The pipeline is fixed and has no bypass: observe, plan, approve, apply, verify.

2 · Final agent-native architecture

Three adapters over one API, with capability tiers enforced in the service.

  • CLI — JSON output, verbs limited to inspect, plan, explain, request-approval, apply-with-token, verify. No destructive primitive exists to compose.
  • MCP server — local process over standard input and output, shipped inside the bundle, same vocabulary. No HTTP transport, now or later; cloud agents reach Brim only through a local host the user runs.
  • App Intents — read-only intents for Shortcuts, Spotlight and automations, plus one intent that opens a plan for review. Nothing destructive is reachable by unattended automation.
  • Approve is human-only. No API, no tool, no model, no standing exception in V1. Approval returns a single-use token bound to one plan hash, one requester identity and a short expiry.
  • Filesystem strings are untrusted input. Paths and names are delimited and labelled wherever they reach a model. Model output may reference plan steps by identifier and may never name a target.
  • Agent actions are labelled in History with the requesting identity.
  • Must exist now: the plan object, approval tokens, service-side capability enforcement. V1: CLI, MCP, read-only intents. Later: scoped standing policies, unattended reporting, anything autonomous.

4 · Final GPU and performance strategy

CPU-first. No custom Metal in V1 or V2. Rendering is already GPU-composited by the system; hashing is bound by storage bandwidth, where the largest available algorithmic lever measures about 25% on real files read from disk.

Speed comes from six things: read less (bulk enumeration, size class then sparse fingerprint then full hash), never scan twice (event-driven deltas), stream rather than materialise, disable caching on large one-shot hashing passes so Brim does not evict the user's working set, yield to the scheduler with background quality-of-service and thermal back-off, and show partial results immediately.

Budgets are two-sided: every target names what Brim delivers and what it costs, and Brim's own energy cost appears in Brim's own energy view.

5 · Final security model

Five controls constitute the minimum trustworthy architecture: a helper vocabulary that cannot express arbitrary deletion and re-validates independently; code-signing requirements on both ends of every connection; race-immune file operations using verified directory descriptors rather than path strings; Trash-first with an append-only journal written before the first mutation; and approval as a human-only capability.

Prevention: the five above, plus bundles-as-data, a hardened update channel, a minimal pinned dependency set, and the agent capability table.
Detection: append-only journal with requesting identity, launch-time self and helper verification, shape anomalies on plans and rejected connections, agent actions distinguished in History.
Recovery: crash-safe reconciliation from the journal, undo validated against the Trash before it is offered, and complete verified self-removal.

The index is treated as a sensitive asset in its own right: owner-only, never exported without explicit action, never included in diagnostics by default.

6 · Final UI/UX direction

Console shell, document-grade plans. Three-column split view; opaque data surfaces; glass only on sidebar, toolbar, inspector and sheets via standard components, which now also respect the user's own system transparency control.

Review queue as the landing surface, ranked by confidence times impact. Three depths of disclosure and no more. Evidence and capability visible in the row. Verification is the one moment with motion, and it shows expectation against measurement including when they disagree. No permission wall, no onboarding, no score. History is a permanent destination. Keyboard traversal is complete, and the CLI is never the only fast path.

7 · Final analytics and insight strategy

Local only, no telemetry, no accounts, no comparison to anyone. Default-visible: findings that are both new and actionable — footprint growth, new background registrations, artefacts that keep returning. On demand: storage trend, energy history, update status. In History: verified outcomes. Non-existent: health scores, cleanliness percentages, junk trends, streaks, scheduled nags.

History is stored as append-only observations rather than derived summaries, so it survives schema evolution. And Brim says "nothing needs doing" when that is the truth.

8 · What must change in the existing specification

  1. Add the plan as a first-class object. Signed, content-addressed, persisted, readable. This is architectural and cannot be retrofitted — everything in volumes I and II depends on it.
  2. Add the approval token and the human-only approval gate to the V1 core, even before any agent ships.
  3. Restate "no resident process" precisely: no watcher; on-demand services are fine; anything persistent is opt-in, visible, and listed by Brim in its own background-items view.
  4. Give energy sampling a home: an opt-in registered agent, self-policed like any other background item.
  5. Add agent interfaces to V1 scope — CLI and local MCP server — because they are nearly free once the plan API exists, and retrofitting safety around them later is how this goes wrong.
  6. Add self-verification and complete self-removal to V1. The product's central claim is complete uninstallation; Brim must demonstrate it on itself.
  7. Replace round performance targets with two-sided budgets that include cache politeness, quality-of-service discipline and thermal back-off.
  8. Add the four vulnerability classes of §6 to the test plan as explicit regression cases, including a symlink-swap test against the helper.
  9. Codify the UI density rule — table-backed above roughly a thousand rows — as a project convention rather than a per-view judgement.

9 · What remains unchanged

All of volume I's substantive conclusions stand. Positioning as outcomes built on a record. The four-tier evidence model and the shared-file veto. Orphaned versus unclaimed. Reset and archive as first-class lifecycle actions. Updates without a private database, with the source stated per application. Background-item truth plus the guided reversible reset. Three-class developer cleanup. Honest APFS storage accounting with verified deltas. Per-app energy measured from public counters, expressed as a share of a charge, with no predicted battery life. Deterministic explanations as the product and any model as optional presentation. Open engine, paid signed build, no subscription without a recurring cost to justify it. The rejected list, in full — nothing in this volume's research argues for readmitting malware scanning, health scores, memory optimisation, scheduled deletion or an always-on install watcher.
